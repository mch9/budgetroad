# 분석 이벤트 확장 가이드 — 시니어 데이터/PM 관점 (팀 학습용)

> **목적**: 현재 taxonomy v2(`event-taxonomy-v2.md`)는 핵심 퍼널·OKR을 커버한다. 이 문서는 **"그다음 무엇을, 왜 심을지"** 를 데이터 애널리스트 / PM·PO의 사고방식으로 분석한다. 정답 리스트가 아니라 **생각하는 법**을 같이 남긴다.
> **읽는 법**: §1(분석가처럼 생각하기)를 먼저 읽고, §2(관심사별 후보)를 사전처럼 참고. §3(우선순위)에서 다음에 뭘 할지 정한다.

---

## 1. 분석가처럼 생각하기 — 3가지 원칙

### 원칙 1. 모든 이벤트는 "행동할 질문(actionable question)"에 답해야 한다
이벤트를 심기 전 항상 물어라: **"이 숫자가 X로 나오면 우리는 무엇을 바꿀 것인가?"** 답이 없으면 그건 *vanity metric*(보기 좋지만 행동으로 안 이어지는 지표)이다.
- ❌ "페이지뷰 수" — 늘면 좋고 줄면 나쁘지만, **그래서 뭘 할지** 안 나옴
- ✅ "Q7에서 이탈률 40%" — Q7을 고치거나 없앤다는 **행동**이 따라옴

### 원칙 2. 관심사 분리 (Separation of Concerns)
이벤트를 **"퍼널 단계"가 아니라 "어떤 의사결정을 돕는가"로 묶는다.** 같은 클릭도 보는 관심사에 따라 다른 이벤트·속성이 된다.
- 예: '저장 버튼 클릭'은 ① *전환*(얼마나 저장하나) ② *전환 품질*(시도했는데 실패했나) ③ *세그먼트*(어떤 유형이 저장하나) — 세 관심사가 다르고, 각각 필요한 속성이 다르다.
- 이렇게 나누면 **이벤트가 중복·난립하지 않고**, 대시보드도 관심사별 페이지로 깔끔해진다.

### 원칙 3. 데이터 품질이 지표보다 먼저
틀린 데이터로 만든 정확한 차트는 **틀린 확신**을 준다. 측정값보다 ① 유실(전송 실패) ② 오염(테스트·봇 트래픽) ③ 정의 불일치를 먼저 잡아야 한다. (현재 우리 코드는 전송 실패를 조용히 삼키고, preview 테스트가 prod 데이터에 섞인다 — §2-6, §2-10)

## 2. 관심사별 추가 이벤트 후보

각 항목: **답하려는 질문 → 이벤트 → 볼 지표 → 해석·액션 → 우선순위(P0 시급 / P1 / P2) · 난이도**

### 2-1. 유입·귀인 (Acquisition & Attribution)
- **질문**: 사용자는 어디서 오고, 어떤 경로가 좋은 사용자를 데려오나?
- **이벤트**: `service_entered` 확장 → `referrer`, `utm_source/medium/campaign`(첫 진입 1회), `landing_variant`
- **지표**: 채널별 진입수 · 채널별 P(Result Viewed) · 채널별 저장률
- **해석·액션**: "인스타 광고는 진입 많은데 전환 낮음 → 랜딩 메시지 불일치" → 광고 카피/랜딩 정합. 채널별 ROI로 예산 배분.
- **우선순위**: **P0** · 난이도 낮음 (URL 파싱 + first-touch 저장)
- **왜 P0**: 지금은 "전환율"만 알지 "누가 전환 안 되는지(어느 채널)" 모른다. 귀인 없이는 개선 타깃이 안 잡힘.

### 2-2. 온보딩 마찰 (Activation Friction) — 이탈 "지점"을 넘어 "이유"로
- **질문**: 왜 그 질문에서 이탈하나? (어렵나? 길까? 답을 못 정하나?)
- **이벤트**: `onboarding_question_answered`에 `time_on_question_sec`(질문 노출→첫 선택) + `prev_choice_id`(재선택=고민 신호) + `change_count`
- **지표**: 질문별 평균 고민시간 · 재선택률 · "다음 못 누르고 이탈"률
- **해석·액션**: "T5(신혼집 자금)에서 고민시간 2배 + 재선택 多 → 선택지가 모호" → 문구·선택지 단순화. (현재 §3-5는 *어디서* 빠지나만, 이건 *왜*)
- **우선순위**: **P1** · 난이도 낮음 (타임스탬프 + prev 비교)

### 2-3. 전환 품질 (Conversion Quality) — 클릭 ≠ 성공
- **질문**: 저장/공유를 *시도*했는데 *실패*한 사람은 없나? (특히 공유)
- **이벤트**: `share_action_clicked`에 결과 추가 → `share_completed{method, outcome: success|cancel|fail|fallback}` (navigator.share 성공 vs 클립보드 fallback vs 취소 vs 에러)
- **지표**: 시도→완료율 · 환경(OS/브라우저)별 실패율 · PDF 인쇄 취소율
- **해석·액션**: "Windows Chrome에서 공유 fallback 100% → 토스트 안내 부족" → 환경별 UX 분기. **저장률이 낮은 게 의도 부족인지 기술 실패인지** 구분(핵심!).
- **우선순위**: **P0** · 난이도 중 (share/print 결과 콜백 계측)
- **왜 P0**: KPI(저장률)의 분모가 "버튼 클릭"이라, 실패를 모르면 **개선 방향을 정반대로 잡을 수 있다.**

### 2-4. 리텐션·루프 (Retention & Loops)
- **질문**: 누가, 왜, 언제 다시 오나? 재방문의 트리거는?
- **이벤트**: `service_entered`에 `return_source`(direct/shared_link/search) + `days_since_first` + `result_count_total`(visitor 누적)
- **지표**: D1/D7 재방문율 · 재방문 트리거 분포 · "결과 N개 만든 visitor" 분포
- **해석·액션**: "공유 링크로 재방문한 사람의 저장률이 2배 → 공유가 리텐션 엔진" → 공유 유도 강화.
- **우선순위**: **P1** · 난이도 중 (visitor 단위 누적 — localStorage)

### 2-5. UX 마찰 신호 (Rage / Dead Clicks)
- **질문**: 사용자가 *되는 줄 알고* 눌렀는데 아무것도 안 일어난 곳은?
- **이벤트**: `dead_click`(클릭했는데 DOM 변화·네비 없음), `rage_click`(같은 지점 빠르게 3+회)
- **지표**: dead/rage click 핫스팟(요소별)
- **해석·액션**: "결과 페이지 페르소나 카드를 자꾸 누름 → 사용자는 펼쳐질 거라 기대" → 인터랙션 추가 or affordance 제거.
- **우선순위**: **P2** · 난이도 중 (전역 클릭 리스너 + 휴리스틱)

### 2-6. 성능·데이터 건전성 (Performance & Data Loss)
- **질문**: 느린 기기에서 이탈하나? **우리 데이터를 우리가 믿어도 되나?**
- **이벤트**: `web_vitals{lcp, inp, cls}` (web-vitals 라이브러리), **`event_send_failed`**(현재 `.catch(()=>{})`로 삼키는 실패를 별도 비콘으로 기록)
- **지표**: 성능 분위수(p75 LCP) · 성능대별 이탈률 · **이벤트 유실률**
- **해석·액션**: "p75 LCP 4s + 저사양에서 결과 도달률 급락 → 로딩 최적화". 유실률 높으면 **모든 KPI를 신뢰구간으로 봐야** 함.
- **우선순위**: **P0(유실 로깅) / P1(web vitals)** · 난이도 낮음~중
- **왜 P0**: 원칙 3. 유실을 모르면 지표가 체계적으로 틀어진다(특히 이탈 직전 이벤트가 잘 유실됨 → 이탈 과소집계).

### 2-7. 세그먼트 확장 (Device / Locale / Time)
- **질문**: 누가(어떤 맥락의 사람이) 더 전환하나?
- **이벤트**: 공통 속성에 `device`(mobile/desktop), `viewport`, `language`, `hour_of_day` 추가
- **지표**: 기기별·시간대별·언어별 퍼널
- **해석·액션**: "데스크톱 저장률↑(이미지 저장 숨김인데도) → 데스크톱 전용 CTA". 페르소나(축1)·코호트(축2)에 이어 **3·4번째 분석 축**.
- **우선순위**: **P1** · 난이도 낮음

### 2-8. 에러·엣지 (Client Errors & Edge Results)
- **질문**: 조용히 깨지는 건 없나?
- **이벤트**: `client_error{message, stack_top, route}`(window.onerror), `result_edge{type}`(예산 0/비정상 등)
- **지표**: 에러 발생 세션률 · 에러↔이탈 상관
- **해석·액션**: "특정 답변 조합에서 계산 NaN → 결과 이탈" → 엔진 버그 수정.
- **우선순위**: **P1** · 난이도 낮음

### 2-9. 실험 인프라 (A/B Variant)
- **질문**: 바꾼 게 정말 좋아졌나? (인과)
- **이벤트**: 공통 속성에 `experiment_id`, `variant` 부착(배정 시 1회 `experiment_exposed`)
- **지표**: variant별 모든 OKR 지표 비교(특히 §3-4 Execution 실험)
- **해석·액션**: "만족도 팝업 문구 A vs B → 응답률·저장률 차이" 통계적으로 판단. **현재 Execution OKR은 이 인프라가 있어야 제대로 검증** 가능.
- **우선순위**: **P1** · 난이도 중 (배정 로직 + 부착)

### 2-10. 데이터 거버넌스 (Test 분리 · 스키마 버전 · PII)
- **질문**: 데이터를 장기적으로 깨끗하게 유지하나?
- **이벤트/속성**: `env`(local/preview/prod — 현재 is_dev만이라 **preview 테스트가 prod에 섞임**) · `schema_version`(properties 구조 변경 추적) · PII 미수집 점검
- **지표**: 환경별 분리 집계 · 스키마 버전별 호환
- **해석·액션**: "분석 쿼리는 `env='prod'`만" → 우리 검증 클릭이 KPI 안 망침. 스키마 변경 시 버전으로 쿼리 보호.
- **우선순위**: **P0(env 분리)** · 난이도 낮음
- **왜 P0**: 이번 검증에서 확인됨 — Vercel은 preview도 `NODE_ENV=production`이라 **테스트가 실데이터로 들어간다.** 지금 고치는 게 가장 싸다.

## 3. 우선순위 종합 (Impact × Effort)

| 후보 | 관심사 | Impact | Effort | 우선 |
|---|---|---|---|---|
| 전환 실패 추적(`share_completed`) | 2-3 | 높음 | 중 | **P0** |
| 이벤트 유실 로깅 | 2-6 | 높음 | 낮 | **P0** |
| env 분리(test/prod) | 2-10 | 높음 | 낮 | **P0** |
| 유입 귀인(utm/referrer) | 2-1 | 높음 | 낮 | **P0** |
| 온보딩 마찰(고민시간·재선택) | 2-2 | 중 | 낮 | P1 |
| 세그먼트 확장(기기·시간) | 2-7 | 중 | 낮 | P1 |
| web vitals | 2-6 | 중 | 중 | P1 |
| 리텐션 트리거 | 2-4 | 중 | 중 | P1 |
| 실험 인프라(variant) | 2-9 | 높음 | 중 | P1 |
| 클라이언트 에러 | 2-8 | 중 | 낮 | P1 |
| rage/dead click | 2-5 | 낮~중 | 중 | P2 |

> **다음 한 사이클에 P0 4개**(전환 실패·유실 로깅·env 분리·유입 귀인)만 해도, "저장률이 낮은 게 의도인지 실패인지 / 어느 채널이 문제인지 / 데이터를 믿어도 되는지"를 답할 수 있다 — 지금은 못 답하는 것들.

## 4. 안티패턴 (하지 말 것)

- **모든 클릭 추적**: 이벤트 폭증 → 비용↑·노이즈↑·분석 마비. 관심사에 답하는 것만.
- **Vanity metric**: 총 이벤트 수, 총 클릭 수 — 행동 안 따라오면 버려라.
- **정의 미합의 이벤트**: "저장"이 PDF인지 링크인지 합의 안 하고 심으면 분석 때 싸운다. (우리가 §3에서 분모 단위 합의한 이유)
- **PII 수집**: 이메일·이름·정확한 위치를 `properties`에 넣지 말 것. visitor_id·user_id(UUID)만.
- **사후 정의**: 이벤트 먼저 심고 "이걸로 뭘 보지?"는 거꾸로. 질문 → 이벤트 순서.
